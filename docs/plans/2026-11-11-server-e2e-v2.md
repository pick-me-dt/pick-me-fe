# 실서버 전체 흐름 테스트 — 2차 서버 (2026-11-11)

이 문서는 차량 앱을 2차 기획을 반영한 백엔드(`pick-me-be` `1ef2b1c`, PR #11)에 붙여 확인한 결과입니다. 환경은 Pleos 에뮬레이터, 로컬 Docker, 매장 대시보드입니다.
1차 서버 기준 결과는 [실서버 전체 흐름 테스트 (1차 서버)](2026-11-10-server-e2e.md)에 남겨 두었습니다.

## 1. 띄우는 법

**백엔드** (`pick-me-be` 폴더, Docker Desktop 필요)

```bash
docker compose up --build -d --wait
```

- 상태 확인: `http://localhost:3000/v1/health`
- 매장 대시보드: `http://localhost:3000/dashboard/` (시드 계정 `yangjae`, 비밀번호는 `pick-me-be/src/seed/seed.ts` `staffPassword`)
- 테이크마다 초기화: `curl -X POST localhost:3000/v1/dev/reset` (진행 주문 취소, 품절·영업·준비 시간 복구, 양재 DT점 다음 주문번호 P-021)

**에뮬레이터**: 실행 방법은 [에뮬레이터 게이트 결과](2026-11-10-emulator-gates.md) 1장을 따릅니다.

**앱**: 서버 주소를 빌드 옵션으로 넘깁니다. 주소를 빼면 앱 안의 가짜 서버를 씁니다.

```bash
./gradlew :app:installDebug -Ppickme.serverUrl=http://10.0.2.2:3000
```

**터미널 시연 명령** (`scripts/demo.sh`): 실서버 모드에서도 가짜 서버와 같은 이름을 씁니다.

- 매장 쪽 명령(`accept`·`reject [사유]`·`prepare`·`ready`·`pickup`·`cancel-ok`·`cancel-no`·`sold-out`·`closed`·`clear`)은 시드 직원 토큰(`POST /v1/dev/tokens`)으로 매장 API `/v1/store/*`를 부릅니다. 대시보드 버튼과 같은 API입니다.
- `reject` 사유 기본값은 `BUSY`입니다. 앱에는 Figma 예시 문구 「주문량 증가」로 표시됩니다.
- 서버에 없는 조작은 실패 이유를 돌려줍니다.
  - `price-up`: 가격을 바꾸는 API가 없습니다.
  - `slow`: 응답 지연은 서버가 2분 뒤에 판단합니다.
- `next`(개발 API로 한 단계 넘기기), `refresh`, `server-reset`은 그대로 있습니다.
- 서버 호출은 백그라운드로 보냅니다. 그래서 「완료」는 요청을 보냈다는 뜻이고, 실패는 logcat `PickmeRemote`에 남습니다 (`app/RemoteServerDemo.kt`).

## 2. 확인한 흐름

모두 에뮬레이터 화면 캡처와 서버 응답(`GET /v1/store/orders`)으로 확인했습니다.

| 단계 | 앱 화면 | 서버 |
| --- | --- | --- |
| 홈 | V01 「픽미 양재 DT점 · 4,500원」 | `GET /v1/me/favorites` |
| 예약 확인 | V02 「4,500원 예약 요청」 | 견적 `available: true`, `prepSec 180`, `afterEntrySec 120` |
| 예약 순간 품절 | `sold-out` 후 예약 → V02-SO 「선택한 메뉴가 품절됐어요」 | 예약 409 `SOLD_OUT` + 새 견적 |
| 접수 종료 | `closed` 후 예약 시도 → V02-CL 「매장 예약 접수가 종료됐어요」 | 견적 400 「영업 중인 매장이 아닙니다」 |
| 예약 | V03 「매장에서 예약을 확인 중이에요」 | `PENDING_ACCEPT`, 주문번호 `P-021`, 실시간 `order.status_changed` |
| ETA 전송 | 내비 경로(`navi-route`) 후 첫 값 2,133초(내비 실측 2,160초), 이후 30초마다 모의 감소 | `timing` 계산: 입구 도착 → 예상 수령(+120초) → 시작 추천(−180초) |
| 응답 지연 | 2분 넘게 수락이 없으면 V03-T 「매장 확인이 조금 늦어지고 있어요」 | `acceptOverdue: true` |
| 매장 거절 | `reject` → V03-R 「매장이 주문량 증가로 예약을 받지 못했어요」 | `REJECTED`, `rejectReason BUSY` |
| 매장 수락 | V04-A 「도착에 맞춰 준비할 예정이에요」 36분 · 주문 P-021 | `ACCEPTED` |
| 대시보드 수락 | 대시보드 「수락」 클릭 → 차량 V04-A (P-024) | 대시보드에 시작 추천·예상 수령·입구 도착·ETA 갱신 시각 표시 |
| 앱 다시 열기 | V00-RE 「진행 중인 주문이 있어요 · 현재 상태: 제조 대기」 | `GET /v1/orders?active=true` |
| 취소 요청 | 주문 상세 → 「매장에 취소 요청」 → V06 「매장에 취소를 요청했어요」 | `CANCEL_REQUESTED`, `cancelRequest.statusBefore ACCEPTED` |
| 취소 거절 | `cancel-no` → V06-E 「취소 요청이 승인되지 않았어요 · 현재 주문 상태: 제조 대기」 | `ACCEPTED`로 복귀, `cancelRequest: null` |
| 제조 전 정체 | `delay 4` → 「늦어진 도착에 맞춰 준비할 예정이에요 · 10:00 도착 예정 · 기존 09:56」 | ETA 2,008 → 2,240초, 시작 추천 4분 뒤로 |
| 제조 시작 | `prepare` → V04-B 「매장에서 준비하고 있어요」 | `PREPARING` |
| 제조 후 정체 | `delay 4` → V05 「이미 준비 중이에요 도착하면 수령해 주세요 · 제조 진행 중」 | `delaySec 241` (제조 시작 때 예상 수령 기준). 시작 추천 시각은 제조 후에도 새 ETA로 다시 계산돼 4분 늦어짐. 앱은 제조 후 추천 시각을 화면에 쓰지 않음 |
| 취소 승인 | 제조 중 취소 요청 → `cancel-ok` → V06-D 「매장에서 취소를 승인했어요」 | `CANCELLED`, `cancelReason USER`, `cancelRequest` 유지 |
| 준비 완료 | `ready` → V04-C 「픽업 주문번호 P-021」 | `READY` |
| 수령 완료 | `pickup` → V07 「수령 완료 09:20 · 주문 P-021」 | `PICKED_UP` |

**확인하지 못한 것**
- 수락 전 운전자 취소: 서버는 바로 `CANCELLED`로 끝냅니다(`orders.service.ts`). 앱 V03 화면에는 취소 버튼이 없어 화면으로는 확인하지 않았습니다. 가짜 서버 단위 테스트로만 확인했습니다.
- 매장 취소(`NO_SHOW`·`STORE`): 매핑 단위 테스트로만 확인했습니다.
- ETA 끊김(V04-E): 확인하지 않았습니다.
- 주행(D) 화면: 실서버로는 확인하지 않았습니다. 기어는 Virtual Console로 바꿉니다.

## 3. 아직 서버에 없거나 앱이 메운 것

| # | 서버 동작 | 앱에서 한 일 |
| --- | --- | --- |
| 1 | 매장이 취소를 거절하면 `cancelRequest`를 지우고 이전 상태로 되돌린다. 응답에 「거절됨」 표시가 없다 | 「취소 확인 중 → 진행 상태」 변화를 보고 앱이 거절로 판단 (`RemoteOrderMapping.kt` `cancelRejectedAfter`) |
| 2 | 영업 중이 아닌 매장의 견적은 오류 코드 없이 400 「영업 중인 매장이 아닙니다」 | 메시지 문구로 V02-CL 판단. 서버 문구가 바뀌면 깨진다 |
| 3 | 메뉴 가격을 바꾸는 API가 없다. 예약 409 `PRICE_CHANGED` 처리는 있다 | 가격 변경(V02-PC)은 가짜 서버로만 시연 |
| 4 | 매장 검색 응답에 도착 예상 시간이 없고 거리만 있다 | 매장 버튼에 거리 표시 (1차 때와 같음) |
| 5 | 메뉴 옵션(Regular)이 비어 있다 | 옵션 표시 생략 |
| 6 | 매장 이름은 「픽미 양재 DT점」이고 브랜드가 따로 없다 (Figma: 「픽미 커피 · 양재 DT점」) | 매장 이름만 표시 |
| 7 | 거절 사유 `BUSY`의 서버 문구는 「주문이 많음」 | Figma V03-R 예시 「주문량 증가」로 표시 |
| 8 | 응답 지연 기준 2분(`ACCEPT_OVERDUE_SEC`)이 2차 기획에 명시돼 있지 않다 | 서버 값 `acceptOverdue`를 쓰고, 가짜 서버도 2분으로 맞춤. 기획 확인 필요 |
| 9 | 예약 직후 주문에는 제조 타이밍이 없다(첫 ETA 전) | 타이밍을 비워 두고, 첫 ETA 전송 응답의 주문으로 채움. V03 화면은 시각을 쓰지 않아 영향 없음 |
| 10 | 제조 시작 후에도 `recommendedStartAt`을 새 ETA로 다시 계산한다 (`pickup-timing.ts` `computeTiming`) | 앱 화면은 제조 후 추천 시각을 쓰지 않아 영향 없음. 가짜 서버는 2차 기획 §3대로 제조 시작 때 고정 |
| 11 | 에뮬레이터 위치가 움직이지 않아 내비 남은 시간이 줄지 않는다 (게이트 G3) | 첫 값만 실측, 이후 모의 감소 (`NaviSeededEtaSource`). 서버에는 모두 같은 telemetry로 기록됨 |

## 4. 앱에서 바뀐 점

- **상태·타이밍**: 2차 상태(`PENDING_ACCEPT`·`ACCEPTED`·`CANCEL_REQUESTED`·`REJECTED` 등)를 그대로 단계로 옮깁니다. 제조 타이밍·주문번호·응답 지연은 서버 값을 씁니다. 앱이 하던 타이밍 계산과 1차 서버용 확인(`/confirm`) 처리는 뺐습니다.
- **예약**: 확인한 금액(`expectedTotal`)을 함께 보냅니다. 서버 409에 따라 다르게 처리합니다.
  - `SOLD_OUT`·`PRICE_CHANGED`: 새 견적으로 예약 확인 화면을 다시 보여 줍니다.
  - `ACTIVE_ORDER_EXISTS`: 진행 중 주문을 불러옵니다.
- **텔레메트리**: 필수 값은 `etaSec` 하나입니다. 위치·속도는 알 때만 보냅니다.
- **실시간**: 2차 차량 이벤트 6종을 받아 주문을 다시 조회합니다.
- **터미널 시연 명령**: 실서버 모드에서도 매장 조작 명령을 같은 이름으로 쓸 수 있습니다(1장).
- **응답 지연 기준**: 앱 규칙도 60초에서 2분으로 바꿨습니다. 서버 기본값에 맞춘 것입니다(3장 8번).
